### 实施注记（2026-11-17，读 `pad2pro-pin-diag-20261117-000624.txt` 后修正）

- **活文件里没有 `defaultRateId`**：extreme_gt 接管后的 `<config>` 只有 `maxrefreshsettings="4"`，全文 grep `defaultRateId` 为 0；`maxrefreshsettings` 已经是 4，683 个可见 item 的 `rateId` 也已是 `4-?-?-4`。所以 §3.1 的“defaultRateId=3-1-2-3 是掉 120 的直接原因”**在这台机器当时不成立**——这条 sed 现在是防御性补丁（覆盖仍带该属性的系统原件），别把它当成本机修复的证明。
- **真正缺的是 `defaultMaxRate` 和 `enableWinOverride`**：活文件 683 个可见 item 只有 12 个 `enableWinOverride="false"`，完全没有 `defaultMaxRate`。v1.6.0 的 sed 补这两项，并用 `policy_complete` 验证“到了活文件”而不是只看 `maxrefreshsettings=4`。
- **活文件与副本字节相同（200296 B / 2142 item）**：mountinfo 来源写的是 extreme_gt，但内容与我们的副本逐字节一致（sed 幂等，看不出谁写的）。别用“副本内容对”推断生效；看 `policy_live_src`（mountinfo root 解析）+ `policy_complete`。
- **30 秒轨迹：mode 7(144)→1(120) 掉了 7 次**，每次 1–2 秒自己回来；看门狗 10s 一次抓不到，也不是策略上限（=4 已生效）能拦住的。这说明掉 120 还有运行期投票/boost 层；Stage 2（`min=142.5`）按计划留到 Stage 1 重启实测后再决定。
- **触控 30/30 次 sens=0 smooth=0**：模块开机写的 4/1 没保住。v1.6.0 已实现 Stage 3 触控守护（`apply.sh guard`，1s 巡检、写回回读、6 次/分钟上限、log/off 可切），不再走“写一次不维护”。
- **v1.6.1 追加（用户要求）**：`game_switch_enable` 写 `1`（`TOUCH_GAME_SWITCH`，默认 1，`-1` 不碰），开机一次 + 守护维护；依据仍是 §2 结论——本机只发固件 GAME_ON、不联动 smooth/sensitive，可能与游戏助手互写，日志会记录回退。

## 0. 结论摘要

这次的两个现象是**两条独立的链**，不要用同一个“看门狗调快点”去糊：

1. **触控回退**：不是内核灭屏/充电清档，而是用户态把 `sensitive_level`/`smooth_level` 的 chosen 档写成了 0。
   v1.5.0 的“开机写一次、看门狗不维护触控”是直接原因；没有回退检测，也没有回退日志。
2. **刷新掉 120**：策略覆盖只改了 `maxrefreshsettings` 和**小写** `rateId`，漏了 `<config defaultRateId="3-1-2-3">`
   （默认仍是 120），又缺 `defaultMaxRate="144"` 和 `enableWinOverride="false"`。
   上限虽然放开到 4，但**默认路径**还是 120；看门狗只是事后把 120 拉回 144，所以看到“掉 120 再回 144”。

一句话：**触控要补“回退检测 + 写回”，刷新要补“默认策略”，而不是把看门狗从 10s 调到 1s。**

注意：导出瞬间 `render=144`、`policy=4`，说明**上限/策略总开关已经放开**，问题不在“144 被截断”，
而在“默认选择仍然是 120”和“事后恢复太慢”。

## 2. 触控为什么回退

### 2.1 内核侧不会因为灭屏/充电把 chosen 清零

NT36536 v2 栈（[touchpanel_common_driver.c](https://github.com/OnePlusOSS/android_kernel_modules_and_devicetree_oneplus_sm8750/blob/oneplus/sm8750_b_16.0.0_pad_2_pro/vendor/oplus/kernel/touchpanel/oplus_touchscreen_v2/touchpanel_common_driver.c)）：

- 亮屏 `operate_mode_switch()` 重放的是 `sensitive_level_used_array[ts->sensitive_level_chosen]` / `smooth_level_used_array[...]`，
  **不会把 chosen 改成 0**。
- 充电插拔 `switch_usb_state_work()` 只是把 `*_used_array` 在默认表和 charging 表之间切换，
  chosen 仍是原来的档位；读 `/proc/touchpanel/sensitive_level` 读的是 chosen，不会因为充电变成 0。

所以日志里的 0/0 **不是**“内核灭屏清档”或“充电表切回默认”造成的；一定是用户态把 chosen 写了 0。

### 2.2 用户态有两条路能把 chosen 写成 0

**路径 A：直接写 proc**

`touchpanel_proc.c` 的 `proc_sensitive_level_write()` / `proc_smooth_level_write()`：

```c
if (value < SENSITIVE_LEVEL_NUM)
    ts->sensitive_level_chosen = value;
...
if (!ts->is_suspended)
    ts->ts_ops->sensitive_lv_set(ts->chip_data, raw_level);
```

节点权限是 0666，任何有权限的用户态进程（触控服务、游戏助手、HAL）都能写。

**路径 B：场景通道 `touch_scene_para`**

同一个文件的 `touch_scen_config_write()` 在 `case SENSITIVE_LEVEL:` 里：

```c
if (value == scene_info->sensitive_level) {
    break;              // 只有“值没变”才是 no-op
}
scene_info->sensitive_level = value;
...
ts->sensitive_level_chosen = value;   // 值变了就直接改 chosen
```

这修正了 `docs/touch-research-v1.5.md` §5b 的一个过度结论：

> 旧结论：场景通道的 `sensitive_level:0` 与 proc 直写 chosen=4 “并存不冲突”。

准确说法是：**只有场景通道的值保持 0 不变时才是 no-op**。一旦 ColorOS 把场景值从 0 改成别的（或从别的改回 0），
chosen 就会被改掉；而模块只在开机写一次，不会把它写回来。探针当时看到 `sensitive_level:0` 只是那一刻的快照，
不能证明整个开机周期不拉锯。

### 2.3 为什么模块没有把它拉回来

v1.5.0 的设计是“持久档位、零拉锯”：

- `apply_touch()` 只在 `boot` / `once` 时调用；
- `watch()` 明确不维护触控（AGENTS：“看门狗不维护触控”）；
- `status` 只读当前值，不回写。

于是系统写 0 之后，模块不会发现，也不会恢复；直到下次手动 `once` 或重启。
这是**设计选择**，不是驱动 bug。用户现在要的是“不要回退”，所以这条设计需要改。

### 2.4 回退之后延迟为什么变高

DTS 档位表（`docs/touch-research-v1.5.md` §4）：

| 档 | sensitive raw | smooth raw |
|---|---|---|
| 0（厂商默认） | 255 | 255 |
| 1 | 20 | 32 |
| 4 | 10 | 128 |

- 回退后 `sensitive 0 = 255`，比 `4 = 10` 大 25 倍；`smooth 0 = 255`，比 `1 = 32` 大约 8 倍。
- 如果“raw 越小越灵敏/越少平滑”的方向成立，0/0 就是**最不灵敏、平滑最重**的一档，用户感觉延迟变高是合理的。
- 方向来自 DTS 推断，固件语义闭源，不是官方文档。**用户自己的 A/B 是当前最有力的证据**；
  如果手感相反，只改 `TOUCH_SENSITIVE_LEVEL`/`TOUCH_SMOOTH_LEVEL`，不要改代码逻辑。

建议做一次可复现 A/B：同一支笔/手指、同一绘图 app，分别 `0/0` 与 `4/1`，用 240fps 慢动作拍“落笔→屏幕响应”，
或至少记录主观跟手性；确认方向后再定“pin 到哪一档”。

另外，刷新率掉 120 **本身**也可能让跟手性变差：本机报点率由固件按显示刷新率自适应，用户态没有旋钮
（`docs/touch-research-v1.5.md` §3）。所以“回退后延迟变高”可能是 **0/0 档位 + 120Hz** 的复合效应。
A/B 时尽量把两者分开：固定 144 只改触控档位，或固定 4/1 只改刷新率，否则会把两个原因混在一起。

### 2.5 触控回退的结论

- **直接原因**：模块写一次不维护；系统用户态（最可能是 ColorOS 触控服务/游戏助手，经 proc 或 scene 通道）把 chosen 改成 0。
- **不是**：内核 suspend/charging 清档。
- **要修**：回退检测 + 写回 + 日志（见 §4.4）。只加日志不加写回，用户还是会感觉延迟；只加写回不加日志，下次换 ROM 又不知道谁在改。

## 3. 刷新为什么掉 120

### 3.1 代码级 bug：`defaultRateId` 根本没被改

`post-fs-data.sh` 与 `customize.sh` 现在的 sed 是：

```sh
sed -E "s/rateId=\"([0-9]+)-([0-9]+)-([0-9]+)-([0-9]+)\"/rateId=\"$R-\2-\3-$R\"/g; \
        s/maxrefreshsettings=\"[0-9]+\"/maxrefreshsettings=\"$R\"/g"
```

它匹配的是**小写开头**的 `rateId=`，也就是 `<item ... rateId="3-1-2-3" />`；
但 `<config ... defaultRateId="3-1-2-3" ...>` 里是**大写 R** 的 `RateId`，sed 匹配不到。

在单行 XML 上实测（用同格式 sample）：

```
<config defaultMaxRate=... defaultRateId="3-1-2-3" ... maxrefreshsettings="4" ...>
```

`defaultRateId` 仍是 `3-1-2-3`（=120），只有 `<item>` 被改成 `4-x-x-4`。
这意味着：

- `maxrefreshsettings=4` 只是把**全局上限**放到 144；
- 没有显式 `<item>` 的应用、以及系统自己的默认路径（应用切换动画、窗口 override、浮窗）仍按
  `defaultRateId=3-1-2-3` 选 120；
- 看门狗看到 120 后重写 settings，把实测拉回 144；但策略默认仍是 120，下一次动画/切换又掉回去。

**这就是“掉 120 再升回 144”的最直接代码原因。** 它也能解释为什么 `policy=maxrefreshsettings="4"`
看起来“已生效”，但实际仍会掉 120：`status` 只检查了 `maxrefreshsettings`，没有检查 `defaultRateId`。

### 3.2 `defaultMaxRate` 缺省是 120

同代 OPlus 策略补丁（OnePlus15-165HZ-LTPO，OOS16）的结论：

> 在 `<config>` 上加 `defaultMaxRate="165"`。没有这个属性时默认是 120
> （`PRIORITY_PAD_MIRAGE_TBL`），`adjustRefreshForDefaultMax()` 会把 boost 路径
> （`startAppSwitchBoost`、`limit winOverride`、浮动窗口）全部钳到 120。

我们的策略副本没有写 `defaultMaxRate`，所以即使 `defaultRateId` 改对，动画/窗口 override/浮窗仍可能被钳到 120。
这条来自**同代但不同机型**的社区模块，Pad 2 Pro 上是否同样生效需要真机 A/B；但从日志的“掉 120 后又能回 144”
形态看，非常吻合。

### 3.3 `enableWinOverride` 没关，app 可以自己把频率拉低

同一个参考模块：

> 给每个 `<item>` 加 `enableWinOverride="false"`。否则策略会拿窗口请求
> （`preferredMaxDisplayRefreshRate` / `preferredDisplayModeId`）把频率往下 revise；
> 日志里是 `revised to win request:2`。AOSP 的 CameraServiceProxy 会给相机窗口 30–60 的请求，
> 所以取景器会掉 60。

我们的策略副本没有动 `enableWinOverride`。如果某个 app（浏览器/视频/相机/游戏）请求 120/60，
策略会照办；看门狗再事后拉回 144。用户要“不要掉 120”，这一层必须关（代价：app 不能再自己请求低帧率，
视频/相机也会跑 144，功耗略增）。

### 3.4 `min_refresh_rate=120` 不是“锁 144”，只是“允许 120”

AOSP `DisplayModeDirector`：

- `PRIORITY_USER_SETTING_MIN_RENDER_FRAME_RATE = 3`，投票 `[min, +∞)`；
- `PRIORITY_APP_REQUEST_RENDER_FRAME_RATE_RANGE = 5`，app 的 `preferredMin/MaxRefreshRate` 投票；
- `VoteSummary.applyVotes()` 从高优先级往低优先级应用；
- 当票冲突、`filterModes()` 找不到合法 mode 时，`DisplayModeDirector` 会 `lowestConsideredPriority++`，
  **丢弃低优先级的票**再试。

所以 app 明确请求 120 时，user min 票可能被丢掉，最终选 120；`min=120` 更是直接允许 120。
`min=144` 的老问题是 `max-min=0` → `mRefreshRateChangeable=false`，亮屏 resume 后卡 120（v1.5.2 已实锤）。
**不要因为“想锁 144”就把 min 改回 144。**

### 3.5 看门狗是事后补救，不是预防

`watch()` 的节奏：亮屏稳态 10s 查一次；漂移后重写 min/peak，sleep 2 复查；仍不达标按 10→20→40→60s 退避。
日志里的恢复耗时 12–174s 就是这个节奏的产物。用户看到的是“120 已经发生了，过一会儿才回 144”。

**把 10s 改成 1s 只会让 120 闪得更短，不会让 120 不发生。** 要“不出现 120”，必须让系统**不选择** 120：
策略默认值、`defaultMaxRate`、窗口 override 三件事。

### 3.6 `extreme_gt` 可能盖住我们的策略副本

doctor 的 mountinfo：

```
... /adb/modules/extreme_gt/my_product/etc/refresh_rate_config.xml
    /my_product/etc/refresh_rate_config.xml ...
```

活文件最上层是 **extreme_gt 的 bind**，不是我们的副本。`policy=maxrefreshsettings="4"` 只能说明“有人把上限放到了 4”，
不能说明“我们的 `defaultRateId`/`defaultMaxRate`/`enableWinOverride` 补丁可见”。
如果 extreme_gt 的文件缺这些字段，我们改自己的副本也不会生效。

因此 v1.6 的 `status` 必须从“只看 maxrefreshsettings”升级为“看**活文件**的完整字段”：

- `defaultRateId` 是否为 `4-1-2-4`（或 `4-4-4-4`）
- `defaultMaxRate` 是否为 `144`
- `enableWinOverride="false"` 的数量是否等于 `<item>` 数量
- `maxrefreshsettings` 是否为 4
- 活文件来源（mountinfo）是 extreme_gt 还是本模块/元模块

如果活文件不全，WebUI 应显示“策略被上层覆盖/不完整”，而不是“已生效”。

## 4. 设计

### 4.1 总原则

- **策略源头优先**：让系统不选 120，而不是选了 120 再拉回。
- **运行时兜底**：看门狗保留，但只做 last resort；不再把“10s 内拉回”当成主方案。
- **触控独立守护**：不要把触控巡检塞进刷新看门狗（AGENTS 的“单职责”约定）。
- **可关、可诊断**：每个新行为都有配置开关；触控默认 `pin`（满足“不回退”），但保留 `log` 只记录模式用于排查，避免再次形成旧版 5s 拉锯。
- **验证优先**：没有真机证据的字段（`defaultMaxRate`、`min=142.5`、chmod 锁）不设成不可逆默认。

### 4.2 策略层（必做，Stage 1）

改 `post-fs-data.sh` 与 `customize.sh` 的 sed（两处必须同步，安装时和每次开机都会生成）：

```sh
R=${POLICY_RATE:-4}
DM=${POLICY_DEFAULT_MAX_RATE:-144}
WIN=${POLICY_WIN_OVERRIDE:-all}

sed -E \
  -e "s/defaultRateId=\"([0-9]+)-([0-9]+)-([0-9]+)-([0-9]+)\"/defaultRateId=\"$R-\2-\3-$R\"/g" \
  -e "s/rateId=\"([0-9]+)-([0-9]+)-([0-9]+)-([0-9]+)\"/rateId=\"$R-\2-\3-$R\"/g" \
  -e "s/maxrefreshsettings=\"[0-9]+\"/maxrefreshsettings=\"$R\"/g" \
  -e "s/ defaultMaxRate=\"[0-9.]*\"//g" \
  -e "s/<config ([^>]*defaultRateId=\"[^\"]*\")/<config defaultMaxRate=\"$DM\" \1/" \
  "$SRC" > "$TMP"
```

补充：

- `defaultRateId` 必须单独一条（大小写不同，不能靠 `s/rateId=/` 顺带匹配）。
- `defaultMaxRate` 先删后加，保证幂等；`$DM` 用 Hz 值（144），不是 rateId。
- `enableWinOverride` 只在 `WIN=all` 时做：

```sh
sed -E -i \
  -e 's/ enableWinOverride="[a-z]+"//g' \
  -e 's|<item ([^>]*[^/])[ ]*/>|<item \1 enableWinOverride="false" />|g' \
  "$TMP"
```

- 如果 `POLICY_FORCE_ALL=1`，把上面两条 rateId 替换改成 `"$R-$R-$R-$R"`（四段全 4），否则保持 `4-1-2-4`
  （只把 auto/120 两档放到 144，90/60 档保留原值）。
- **校验后再覆盖**（避免把坏文件交给元模块合并）：
  - 文件含 `<refresh_rate_config`、`<config `；
  - **最后一个** `<config ...>`（真正的配置，不是头注释）里 `defaultRateId="$R-1-2-$R"`；
  - 同一个 `<config>` 里 `defaultMaxRate="$DM"`；
  - `maxrefreshsettings="$R"`；
  - `<item ` 数量 == `enableWinOverride="false"` 数量（`WIN=all` 时）；
  - 行数不变（单行 XML 至少检查字节数不为 0，且 `<config` 仍在）。
  - 任一条不满足：保留旧副本，写 `post_fs.log`，不要合并坏策略。

如果活文件被 extreme_gt 盖住且字段不全：默认只报 `policy_complete=0`，**不抢层**。
用户明确要求时，提供 `POLICY_TAKEOVER=1`（默认 0）：在元模块合并后把本模块完整副本 bind 到活文件，
挂后回读字段并记日志；失败自动 umount/不启用。这是最后手段，不默认，且必须在文档里写清与 extreme_gt 的冲突。

`customize.sh` 的生成逻辑与 `post-fs-data.sh` 保持一致；建议把这段 sed 抽成 `tools/` 之外的一个小函数？
本仓库没有公共 lib，且 AGENTS 要求 `customize.sh`/`post-fs-data.sh` 都能独立跑；复制同一段并加注释“两处同步”更稳。

### 4.3 运行时（Stage 2，可选但推荐）

- **先不改 `REFRESH_MIN`**。Stage 1 修好 `defaultRateId` + `defaultMaxRate` + `enableWinOverride` 后，
  观察 10 分钟是否还掉 120。如果还掉，再做 Stage 2。
- Stage 2 的候选：`REFRESH_MIN="142.5"`。
  - AOSP 判据 `max-min>1 && max>60`：144-142.5=1.5>1 → `changeable=true`，避开 min=144 的 resume 卡 120。
  - min 票 `[142.5, +∞)` 会让 120 不是合法 mode；但如 §3.4 所述，app 请求冲突时 min 票可能被丢弃，
    所以**它不能替代策略层**，只是兜底。
  - 必须先做 30 秒 A/B：写入 142.5 → 看 `mActiveModeId` 是否 7、`mRefreshRateChangeable` 是否 true、
    灭亮屏后是否仍 144。如果 ColorOS 把 min round 成 144 → `changeable=false` → **不要用**，回退 120。
- 看门狗保留现有退避/限频；只在日志里补充上下文（`defaultRateId`/`defaultMaxRate`/`win_override`/前台 app），
  便于下次确认是“策略没生效”还是“app 自己锁 120”。

### 4.4 触控 pin（Stage 3）

独立守护进程 `apply.sh touch-daemon`（或 `touch_guard()` 子进程），不要塞进 `watch()`：

```sh
TOUCH_GUARD="pin"          # pin=检测到回退就写回; log=只记录; off=关闭
TOUCH_GUARD_INTERVAL="1"   # 亮屏轮询秒; 灭屏 10s
TOUCH_GUARD_MAX_WRITES="6" # 每分钟最多写回次数, 超过退避
TOUCH_LOCK="0"             # 1=尝试 chmod 0444 锁 proc 节点(实验, 默认关)
```

行为：

1. 只在亮屏时按 `TOUCH_GUARD_INTERVAL` 读 `sensitive_level`/`smooth_level`（两个 `cat`，成本可忽略）。
   亮屏判断不要每秒 `dumpsys power`：优先 `/sys/kernel/oplus_display/power_status` 或背光 brightness 节点，
   没有则 5s 缓存一次 `dumpsys power`。
2. 值与 `TOUCH_SENSITIVE_LEVEL`/`TOUCH_SMOOTH_LEVEL` 不一致时：
   - 记录一行：`触控回退: sensitive 4->0 (scene=... charge=... fg=... screen=...)`；
   - `echo "$want" > /proc/touchpanel/$node`；
   - **写完回读**；回读仍不是 want 算失败，进入退避并记日志（不要只信 echo 的返回值，驱动可能 clamp）；
   - 计数 `touch_fallback++`。
3. 同一节点一分钟内写回超过 `TOUCH_GUARD_MAX_WRITES`：退避到 5s，并记一条“外部写入持续”的警告，
   避免和 ColorOS 形成每 1s 的拉锯刷屏。
4. 节点不存在（OTA 换栈）→ 只记一次，跳过；绝不盲写。
5. `TOUCH_GUARD=log` 时只记录不写回，用于先确认“是谁、在什么场景”改的；确认后再切 `pin`。
6. 可选 `TOUCH_LOCK=1`：写入目标档位后 `chmod 0444` 两个 proc 节点（root 仍可写），
   试图从权限层阻止系统用户态写入。**这是实验项**：system_server/触控服务可能有 CAP_DAC_OVERRIDE，
   也可能在 resume 后重建节点；必须先真机验证，且默认关闭。
7. `service.sh` 启动守护；`uninstall.sh` 杀两个 PID；`status` 增加 `touch_daemon`/`touch_fallback`/`touch_scene`。

为什么保留 `log`：现有结论对“场景通道是否覆盖”判断过强；首次排查可临时切 `log` 跑一个开机周期，记录
`touch_scene_para` 和前台 app，确认是 proc 直写还是 scene 通道，再决定是否需要 `TOUCH_LOCK`/排除某些游戏。
默认 `pin` 是为了满足“不回退”；如果 `pin` 后出现持续拉锯，再切 `log` 定位，而不是直接提高写回频率。

### 4.5 状态与 WebUI（v1.6.0 已实施）

`status` 新增（只追加，不改旧键）：

```

default_rate_id=4-1-2-4                  # 活文件；空=文件没有这个属性（本机就是空）

```

WebUI（实际实现）：

- 只有两张卡：「实测刷新率」「触控档位」；看门狗/策略压成一行小字。
  - 刷新率卡：render 达标→good；`render=120` 且 `refresh_changeable=false`→warn「固定刷新率模式」。
  - 触控卡：实际档位 == `touch_target_*`→good；不等→warn 且 detail 写「目标 4 / 1 · 守护写回中 · 已写回 N 次」；节点不可读→warn。

- 只读约定不变：不写 config、不触发 once、不渲染日志；导出只保留 `tail -n 200` 日志与策略摘要。

### 4.6 诊断脚本（v1.6.0 已实施）

`tools/diag_pin.sh`（只读、不参与安装；已同时放到
`/storage/emulated/0/Download/Code/Module/diag_pin.sh` 方便真机直接跑），输出到
`/storage/emulated/0/Download/Code/Module/pad2pro-pin-diag-<时间>.txt`，
目录不可写时回退 `/sdcard/Download/Code/Module/`，再回退 `/data/local/tmp/`。采集：

1. 四个策略文件**摘要**：`<config>` 行 + item/win_false/rateId 计数 + `defaultMaxRate`/`defaultRateId` + sha256 + 前 15 行；
   `PAD2PRO_DIAG_FULL=1` 才输出全文（旧版默认 64KB×3，单份日志 245KB）；
2. extreme_gt、本模块副本、`/data/system/refresh_rate_config.xml` 对照（同摘要口径）；
3. `mountinfo` 只留 `src=`/`mount=` 两列，不再整行；
4. `sys_dynamic_frame_config.xml` / `oplus_vrr_config.json` 只出 enable/targetFramerate 计数/adfr 等关键字段
   （**不要改 `targetFramerate=144`**：同代 OPlus 解析器只认 120/90，144 会让整个动画配置解析失败）；
5. settings 五项（peak/min/oplus/user/oplus_refreshrate_override）；
6. `dumpsys display` / `dumpsys SurfaceFlinger` 的 mode/specs/changeable/OPlusRefreshRateSelector；
7. `/proc/touchpanel/{sensitive_level,smooth_level,touch_scene_para}` 与节点权限；
8. **`p2p.log` 尾部 200 行**——判断模块开机到底有没有写触控、守护有没有写回；
9. 30 秒 1Hz 轨迹：mode/hz/changeable/触控档位/scene/前台 app/充电/亮灭屏。
   跑的时候让用户切换 app、锁屏解锁、插拔充电器——这能同时抓刷新掉 120 和触控回退的现场。

## 6. 真机验证（按顺序）

### Stage 1：策略补丁（先只改策略，不改 min/触控）

1. 跑 `tools/diag_pin.sh` 留底；确认活文件 `defaultRateId` 是不是 `3-1-2-3`、有没有 `defaultMaxRate`。
2. 装 v1.6 Stage 1，重启；`post_fs.log` 应显示副本校验通过；`status` 应显示
   `default_rate_id=4-1-2-4`、`default_max_rate=144`、`win_override=all`、`policy_complete=1`。
   - 如果活文件仍是 extreme_gt 且字段不全：说明被上层盖住，先解决图层（停用 extreme_gt 的策略文件，或让它的作者加字段），
     不要在本模块里盲目加 bind。
3. 连续 10 分钟：切 10 个 app、进/出设置、锁屏解锁 3 次、播 1 分钟视频、开关一次相机；
   同时每 500ms 采 `mActiveModeId`（或用 `diag_pin.sh` 的 30s 轨迹）。
   验收：**mode=1（120）出现 0 次**；mode=5（60）如果只在灭屏/亮屏瞬间出现，单独记录，不阻塞本阶段。
4. 看 `p2p.log`：不应再出现“漂移 120Hz”刷屏；偶尔一次也要有上下文日志。

### Stage 2：`min=142.5` A/B（仅当 Stage 1 仍有 120）

1. 临时 `settings put system min_refresh_rate 142.5`（用 `setting_put` 的回退链；ksu 域可能被拒）。
2. 等 3s：`mActiveModeId=7`、`mActiveRenderFrameRate≈144`、`mRefreshRateChangeable=true`。
3. 灭屏 10s → 亮屏：仍 144（不是卡 120）。
4. 切一个会请求 120 的 app：如果仍能掉 120，说明 min 票被 app 请求丢弃（符合 AOSP 行为），
   回到策略层 `enableWinOverride=false` 解决；不要把 min 改成 144。
5. 任何一步出现 `changeable=false` 或 resume 卡 120 → 立即回退 120，Stage 2 不采用。

### Stage 3：触控 pin

1. 首次排查可临时 `TOUCH_GUARD=log` 跑一个开机周期：切 app、锁屏解锁、插拔充电、进/出游戏；看 `p2p.log` 里
   `触控回退` 行的 `scene`/`fg`/`charge`。默认 `pin` 也会记录这些行，只是同时写回。
2. 确认回退场景后切 `pin`；重复上述操作，`touch_sensitive/touch_smooth` 应始终 4/1，
   `touch_fallback` 只应在系统主动改档时 +1，且日志有对应行。
3. 如果 `pin` 后每分钟写回 >6 次：说明系统在持续拉锯，先看日志定位（是否某个游戏/场景），
   再决定是 `TOUCH_LOCK=1` 实验还是 `log` 模式放过该场景；不要无脑提高写回频率。
4. 延迟 A/B：0/0 vs 4/1，确认方向和用户主观感受一致。

### 验收标准

- 刷新：10 分钟混合使用，`mActiveModeId=1` 采样 0 次；`p2p.log` 无“漂移 120Hz”。
- 触控：`sensitive_level=4`、`smooth_level=1` 在切 app/锁屏/充电后仍成立；`touch_fallback` 不持续增长。
- 状态：WebUI 刷新卡显示“144 已锁定”且 `policy_complete=1`；触控卡显示当前档位与回退次数。
- 回退：任何新策略校验失败都不合并坏文件；`POLICY_*` 关掉后不残留旧副本（沿用现有 `POLICY_ENABLE=0` 逻辑）。

## 7. 风险与未决

| 风险 | 说明 | 处理 |
|---|---|---|
| `defaultMaxRate` 在 Pad 2 Pro 是否同样生效 | 证据来自 OnePlus 15/OOS16 同代模块，不是本机 | Stage 1 真机 A/B；不生效就只保留 `defaultRateId` + `enableWinOverride` |
| `min=142.5` 被 ColorOS round/忽略 | 可能变 144 → changeable=false，回到 resume 卡 120 | A/B 不过就不采用；不要用 144 |
| 活文件被 extreme_gt 盖住 | 我们的副本字段再全也不可见 | `status` 报 `policy_live_src`/`policy_complete`；用户决定停用/更新 extreme_gt，或显式接受 runtime-only |
| 触控写入者未知 | 可能是 proc 直写，也可能是 scene 通道 | 先 `TOUCH_GUARD=log` 抓一个周期；`pin` 只写 proc，不写 scene，避免把 scene 的“最后值”改成 4 后反而让系统的 0 生效 |
| 触控方向闭源 | 0/4 哪个更跟手没有官方文档 | 用户 A/B；只改 config 默认值，不改逻辑 |
| 策略文件 OTA 改格式 | 单行 XML、字段名可能变 | 生成后校验；失败保留旧副本并记日志；不盲目 sed |
| `sys_dynamic_frame_config.xml` | 同代解析器只认 120/90，写 144 会破坏动画配置 | 默认不碰；只做只读诊断 |

## 8. 最小止血补丁（v1.6.0 已按此实施，但前提已修正）

**v1.6.0 实际实现**：`defaultRateId` 改写（防御性，活文件没有就不生效）+ `defaultMaxRate` 先删后加 +
每个 `<item>` 加 `enableWinOverride="false"`，全部在临时文件上做并校验通过后才覆盖副本
（校验项与 `post-fs-data.sh` 的 `validate_copy` / `apply.sh` 的 `policy_complete` 一致）。

注意：真机日志显示**活文件可能没有 `defaultRateId`**（extreme_gt 接管后就没有），所以“只修 defaultRateId”
在这台机器上什么都不会发生；真正缺的是 `defaultMaxRate` 与 `enableWinOverride`。改完重启一定用
`status` 的 `policy_complete=1` 验证，不要只看 `maxrefreshsettings=4`。

`post-fs-data.sh` 和 `customize.sh` 的 sed 各加一条：

```sh
-e "s/defaultRateId=\"([0-9]+)-([0-9]+)-([0-9]+)-([0-9]+)\"/defaultRateId=\"$R-\2-\3-$R\"/g"
```

改完重启，确认活文件里：

```sh
grep -o '<config [^>]*>' /my_product/etc/refresh_rate_config.xml
# 期望 defaultRateId="4-1-2-4" maxrefreshsettings="4"
```

如果活文件是 extreme_gt 的 bind，先确认它的文件是否也有 `defaultRateId="4-1-2-4"`；
没有的话，这一条改了也不会可见——这就是 §3.6 要先诊断的原因。
